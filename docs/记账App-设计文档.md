# 记账汇总分析 App — 设计文档（Spec）

> 版本：v1 设计稿　日期：2026-05-31
> 这份文档定义"做什么"和"为什么"，不含逐行代码。实现计划在它通过之后单独产出。

---

## 1. 项目目标（一句话）

把**支付宝**和**微信**两边分散的账单合并到一起，自动分类，用图表直观看出"我的钱到底花在哪"。

核心使用节奏：**每月导入一次**做复盘，不追求实时。

### 要解决的真实痛点
- 支付宝、微信两份账单分开看，看不出总的消费结构。
- 手动逐条记账坚持不下来。

### 明确不做的事（v1 范围之外）
- ❌ 后台实时自动捕获（已论证：保活不可靠、规则易碎，且与"按月复盘"目标不符）
- ❌ AI 分类（CSV 自带分类字段，本地规则足够；AI 留作以后可选开关）
- ❌ 直接在 App 内解密微信加密压缩包（v1 先手动解压）
- ❌ 银行短信、云同步、多用户、记账提醒

## 2. 形态与技术选型

### 形态
**单页网页 App（PWA）**，部署到公网拿到一个网址，手机浏览器打开后「添加到主屏幕」，桌面上就是一个图标，点开全屏运行，与原生 App 体验一致。

选它的决定性理由：数据源已变成"导出的文件"，原生安卓唯一的优势（读手机实时数据）在本项目里用不到；而网页对零基础者上手最快——无需 Android Studio / Gradle / 模拟器，改一行代码刷新浏览器即生效。

### 技术栈
| 类别 | 选型 | 用途 |
|---|---|---|
| 结构/样式/逻辑 | HTML + CSS + 原生 JavaScript | 不引入框架，降低门槛 |
| CSV 解析 | PapaParse (CDN) | 正确处理带逗号的字段 |
| Excel 解析 | SheetJS / xlsx (CDN) | 解析微信 .xlsx，并把 Excel 序列号转日期 |
| 中文解码 | 浏览器内置 `TextDecoder('gbk')` | 支付宝 CSV 是 GBK 编码 |
| 图表 | Chart.js (CDN) | 饼图、趋势图 |
| 本地存储 | IndexedDB | 账单数据 + 分类规则，全部存本机 |
| 部署 | Netlify 或 GitHub Pages | 免费、自带 HTTPS（PWA 必需） |

### 隐私保证（重要）
- 所有解析、分类、统计、存储**全程在手机浏览器本地完成**，数据存在 IndexedDB，**一个字节都不上传任何服务器**。
- "代码部署在公开网址"≠"账单公开"。公开的只是不含任何数据的程序代码。

## 3. 真实数据格式（已逐一验证，非猜测）

### 3.1 支付宝 CSV
- **编码：GBK**（用 UTF-8 直接读会全是乱码，必须用 `TextDecoder('gbk')`）。
- **结构**：第 1–23 行是账户/统计/特别提示等说明文字，**第 24 行才是真正的列头**。
  解析策略：逐行扫描，找到以 `交易时间` 开头的那一行作为列头起点（不写死行号，防止格式微调时崩）。
- **12 列**（顺序固定）：

  `交易时间, 交易分类, 交易对方, 对方账号, 商品说明, 收/支, 金额, 收/付方式, 交易状态, 交易订单号, 商家订单号, 备注`

- **关键字段取值**：
  - `收/支`：`支出` / `收入` / `不计收支`
  - `交易状态`：`交易成功` / `交易关闭` / `退款成功` / `等待确认收货` / `还款成功`
  - `交易分类`：餐饮美食 / 交通出行 / 日用百货 / 文化休闲 / 充值缴费 / 商业服务 / 数码电器 / 服饰装扮 / 退款 等（**自带分类，质量高**）
- **坑**：订单号字段尾部带一个**制表符**，作为去重键前必须 `trim()`。

### 3.2 微信账单 .xlsx
- **格式：二进制 Excel**（不是 CSV！必须用 SheetJS 解析），内部文本为 UTF-8。
- **结构**：前 14 行是说明文字，第 15 行（`----…微信支付账单明细列表----`）后是列头。
  解析策略：同样按"找到 `交易时间` 表头行"定位。
- **11 列**（顺序固定）：

  `交易时间, 交易类型, 交易对方, 商品, 收/支, 金额(元), 支付方式, 当前状态, 交易单号, 商户单号, 备注`

- **关键字段取值**：
  - `收/支`：`支出` / `收入` / `中性交易`（充值/提现/理财通/零钱通存取/信用卡还款 计入中性交易）
  - `当前状态`：`支付成功` / `已转账` / `已存入零钱` 等
  - `交易类型`：扫二维码付款 / 商户消费 / 转账 等（偏行为，不是消费品类，分类价值低于支付宝）
- **坑**：`交易时间` 存的是 **Excel 序列号**（如 `46173.60`），不是文本日期，必须让 SheetJS 转成真实日期（`cellDates` 选项）。金额是纯数字，好处理。

## 4. 统一数据模型

不论来自哪一方，每笔交易归一成同一种结构：

| 字段 | 含义 | 来源映射 |
|---|---|---|
| `id` | 去重唯一键 | 支付宝`交易订单号` / 微信`交易单号`（trim 后） |
| `source` | 来源 | "支付宝" / "微信" |
| `datetime` | 交易时间 | 统一成标准日期时间 |
| `amount` | 金额（数字） | 支付宝`金额` / 微信`金额(元)` |
| `direction` | 方向 | 支出 / 收入 / 中性（不计收支/中性交易归此） |
| `counterparty` | 交易对方 | 两方同名字段 |
| `description` | 商品说明 | 支付宝`商品说明` / 微信`商品` |
| `rawCategory` | 原始分类 | 支付宝`交易分类` / 微信`交易类型` |
| `myCategory` | 我的统一分类 | 见第 6 节，规则生成、可手动改 |
| `status` | 交易状态 | 两方对应字段 |
| `payMethod` | 支付方式 | 支付宝`收/付方式` / 微信`支付方式` |
| `note` | 备注 | 两方`备注` |

## 5. 合并、去重、过滤逻辑

这是项目真正的价值所在。分三步：

### 5.1 去重（同源重复导入）
- 以 `id`（订单号 trim 后）为唯一键。
- 重复导入同一个月、或导入有时间重叠的两份文件，相同 `id` 只保留一条，**不会重复计账**。这是 CSV/Excel 路线相比短信/截图最大的优势——订单号天然唯一，无需靠"金额+时间"去猜。

### 5.2 跨源说明
- 一笔钱要么走微信、要么走支付宝，**同一笔交易不会同时出现在两边**。所以合并的本质是"拼接"而非"跨源去重"，跨源重复极少。

### 5.3 过滤"非真实消费"
默认在**统计**时排除以下项（但仍存库、可在明细里查看，开关可调）：
- `direction` = 中性（不计收支 / 中性交易）→ 这是钱在自己账户间挪动（充值、提现、理财、还款、转账到自己），不是花销。
- `status` = `交易关闭`（支付宝）→ 下单后未实际支付，不应计入。

### 5.4 退款处理（v1 简化方案）
对照真实数据：一笔被退款的交易，**原单状态会变成 `交易关闭`，并另外生成一条 `不计收支 / 退款成功` 的记录**（样本中可见成对出现）。这两类在 5.3 中都已被排除，因此**退款已被自动抵消为零，v1 无需再做额外扣减**（早先设想的"从分类里扣减退款"会导致重复扣减，已废弃）。
- 因此 v1 的口径就是 5.3 一条：只统计 `direction=支出` 且 `status≠交易关闭` 的记录。
- 极少数"原单已成功、事后部分退款"的情况，v1 暂不精细配对，作为已知局限（见第 9 节）；"按商家订单号配对原单与退款"列为后续优化项。

## 6. 分类（纯本地规则）

### 统一分类体系（学生版 v1，可调）
`餐饮` / `交通` / `购物` / `学习教育` / `娱乐休闲` / `话费通讯` / `生活缴费` / `医疗健康` / `人情往来` / `其他`

各类含义（贴合学生日常，括号内为真实样本中出现过的典型商户）：
| 分类 | 涵盖 | 真实样本示例 |
|---|---|---|
| 餐饮 | 外卖、食堂、饭店、奶茶饮料 | 美团、乡村基、蜜雪冰城、淘宝餐饮券 |
| 交通 | 地铁公交、打车、共享单车、火车 | 北京轨道交通、高德打车 |
| 购物 | 日用百货、服饰、数码、电商 | 淘宝/天猫平台商户、服饰装扮 |
| 学习教育 | 打印复印、书籍文具、课程培训、考试报名 | 嘉园打印室、运营与交流培训 |
| 娱乐休闲 | 游戏、视频/音乐会员、电影、文化休闲 | Steam、Valve |
| 话费通讯 | 手机话费、流量、宽带 | 充值缴费类 |
| 生活缴费 | 校园卡/一卡通充值、水电、宿舍相关 | "1元充值"、各类小额充值 |
| 医疗健康 | 药店、医院、体检 | （样本中暂无，预留） |
| 人情往来 | 给他人的转账、发出的红包 | 微信转账 |
| 其他 | 未命中以上任何一类 | 兜底 |

> 这套是初版，做出来后你可以随时增删或改名（比如想把"房租""恋爱支出"单列）。

### 分类优先级
1. **商户记忆优先**：若 `counterparty` 命中用户历史手动分类，直接采用（最高优先级）。
2. **支付宝原始分类映射**：`交易分类` → 统一分类（餐饮美食→餐饮、交通出行→交通、日用百货/服饰装扮/数码电器→购物、文化休闲→娱乐休闲、教育培训→学习教育、充值缴费→生活缴费/话费通讯）。覆盖率高。
3. **关键词规则**：对微信、或支付宝未命中的，用 `counterparty` + `description` 关键词匹配。初版关键词举例：
   - 餐饮：美团、饿了么、瑞幸、蜜雪、星巴克、餐饮、外卖、奶茶
   - 交通：地铁、公交、轨道交通、高德、滴滴、打车、单车、火车
   - 学习教育：打印、文印、图书、书店、文具、培训、教育、学费
   - 娱乐休闲：Steam、Valve、游戏、会员、视频、音乐
   - 购物：淘宝、天猫、京东、拼多多、超市
   - 话费通讯：话费、流量、移动、联通、电信
   - 生活缴费：校园卡、一卡通、充值、水电
   - 人情往来：转账、红包（且对方为个人）
4. **兜底**：都没命中 → `其他`，在 UI 高亮提示，等用户手动归类。

### 商户记忆
- 用户手动把某笔归类后，记住 `counterparty → myCategory` 映射，存 IndexedDB。
- 下次同一商户的交易自动套用。这是"越用越省心"的关键，也是替代 AI 的核心机制。

## 7. 界面与功能

### 主要页面
1. **导入页**：选择文件（支付宝 .csv / 微信 .xlsx），自动识别来源，显示"本次新增 N 条、去重跳过 M 条"。
2. **仪表盘**：
   - 时间范围选择（默认本月 / 可选某月）。
   - 总支出、总收入、净额。
   - **分类占比饼图**（直接回答"钱花哪了"）。
   - 按日/按月支出趋势。
3. **明细页**：可按分类/来源/时间筛选的交易列表；点单条可改分类（触发商户记忆）；高亮"未分类/其他"项。

### 交互原则
- 面向零基础作者本人使用，界面以"看清结构"为先，不堆砌功能。
- 手机竖屏优先。

## 8. 分阶段实现路线（每阶段都能在手机上看到东西在动）

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **0 骨架** | 单页空壳，能部署、能在手机主屏打开 | 手机点图标能打开一个空白页 |
| **1 解析+列出** | 导入两种文件，正确解码中文/转日期，表格列出所有交易 | 两份真实文件导入后，中文不乱码、时间正确、条数对得上文件头部的统计 |
| **2 持久化+去重** | 存 IndexedDB，重复导入按订单号去重，过滤中性/废单 | 同一文件导入两次，账目不翻倍；中性交易不计入支出 |
| **3 分类+手动改** | 规则自动归类，未命中高亮，手动改并记住商户 | 大部分交易自动归类；手动改一次后，该商户后续自动归对 |
| **4 仪表盘** | 饼图+趋势+汇总 | 能一眼看出当月各分类占比与总支出 |
| **5 PWA** | manifest + service worker，部署，加主屏，离线可开 | 断网也能打开 App 看已存数据 |

> 每个阶段交付一个能跑的版本，确认无误再进入下一阶段。第 1 阶段会直接用你提供的这两份真实文件做验收。

## 9. 已知风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 微信只能导出加密 zip（邮箱发送） | 每月导入前需手动解压 | v1 接受手动解压；App 内解密列为后续可选 |
| 支付宝/微信改版导致导出格式变化 | 解析可能失效 | 用"找表头行"而非写死行号；列按表头名取值而非死索引，提升健壮性 |
| 退款/废单口径 | 统计金额偏差 | v1 用 5.3/5.4 的简化规则；精细配对列为后续 |
| 微信"交易类型"分类价值低 | 微信交易更多落入"其他" | 靠关键词规则 + 商户记忆补足 |
| 浏览器换设备/清缓存导致 IndexedDB 丢失 | 数据丢失 | v1 提供"导出/导入 JSON 备份"作为兜底（列入阶段 4 或 5） |

## 10. 成功标准

v1 算成功，当且仅当：
1. 把支付宝 + 微信两份真实账单导进去，**不乱码、不重复、不把转账当消费**。
2. 大部分交易**自动归好类**，少数手动归一次后能被记住。
3. 仪表盘能**一眼看出当月钱花在哪几类、各占多少**。
4. 全程**数据不出本机**，手机上像个正常 App 一样点图标就能用。
